# 秒懂 CLI（md）第 3 步 · 3a 设计：知识库只读与「没召回」排查

> 2026-09-25。接第 2 步 spec（`2026-09-24-miaodong-cli-step2-design.md`），沿用 md 的身份、区和企业的换算、输出约定与退出码。
>
> 第 3 步做知识库，分三段，每段各自设计、计划、验收：
> - **3a 只读与排查**（本文）；
> - **3b 导入秒懂**；
> - **3c 资料处理**：把 rag-file-ingestion 融进 md。
>
> 3c 的产出就是 3b 的输入，所以先定 3b 的导入格式。3a 最小、没有风险，后两段的验收也要靠它读回核对。
>
> 依据：
> - 用户整理的《秒懂接口大全》（`~/Desktop/秒懂接口.md` 第 2、6、10、12 章）；
> - 09-25 在兴趣岛独立部署（xlink-insight，前端 1.18.4）上的只读探测：8 轮，全是 GET 或列表查询，没写任何东西；
> - 本机拉过的画布工作副本。
>
> 证据标记：【实测】09-25 探测时真调过、看到了响应；【文档】只在《秒懂接口大全》里有，该章只对照 I 区 1.17.3 的前端代码核对过；【推】推断。

## 1. 要解决的问题与验收

用户 09-25 给的两个原因：
1. **很多 case 是知识库里有、但这次没检索到。** md 现在能看知识库节点当时召回了什么（`md exec --node`），也能重跑（`md trial`），但看不到库里有什么、每条是什么状态。AI 查到这一步只能停下，让人去控制台翻。
2. **客户给的资料各种格式都有**，想用 md 处理后导进秒懂知识库。这是 3b、3c 的事，不在本文。

探测看到的现状（兴趣岛）：
- 37 个知识库里有 36 个是纯 FAQ，最多的一个 2725 条；只有 1 个有文件，没有网页和视频【实测】。
- 抽查的一个库有 140 条 FAQ，其中 11 条未审核；未审核的 FAQ 语义搜索搜不到【实测】。所以「库里有但没检索到」至少有一类原因，现在就能直接查出来。

**验收**：

| 指标 | 现状 | 目标 |
|---|---|---|
| 给一条「库里有但没召回」的执行，说出是哪一类原因 | 打开控制台逐条翻 | 1 条 `md kb why`，0 段临时脚本，不用打开控制台 |
| 这个智能体用了哪些知识库，每个节点召回几条、门槛多少 | 在画布里逐个点开节点 | 1 条命令 |
| 一句话在库里有没有、是什么状态、语义分数多少 | 控制台搜索，看不到分数 | 1 条命令 |
| 把一个知识库拉到本机给 AI 查 | 没有 | 1 条命令，条数和平台显示的一致 |
| 对秒懂的写入 | — | 0（本段只读） |

**不做**，以及原因：
- **任何写入**（审核 FAQ、改 FAQ 或段落、导入、上传）：放到 3b。改知识库会立刻对所有引用它的智能体生效，要比推画布更严的闸门，单独设计。
- **删知识库、删文件**：3b 也不做。删知识库会连库里的数据一起删、不可恢复【文档】，留在控制台手动做。
- **文件段落的语义搜索**：没找到接口，文档和探测都只有 FAQ 的。文件型知识库的「分数」交给 `md trial` 判断。
- **知识标签、数据知识库（SQL 表）、FAQ 和文档的抽取任务、网页和视频的内容**：兴趣岛没有这些数据，也没有排查需求，等有了再做。

## 2. 事实基础

### 2.1 接口

都是控制台内部接口，鉴权和 md 现有命令一样：浏览器取的 JWT，`orgId` 放 query。

| 用途 | 请求 | 关键参数和返回 | 证据 |
|---|---|---|---|
| 知识库列表 | `GET /api/knowledge-base/list` | `current`、`pageSize`、`keyword?`；每条有 `id`、`name`、`qaCount`、`fileCount`、`pageCount`、`videoCount`、`modelType`；`page.total` | 实测 |
| 知识库详情 | `GET /api/knowledge-base/details` | `knowledgeBaseId`；返回里的 id 叫 `knowledgeBaseId`，数量叫 `qaCount`、`docCount`、`webCount`、`videoCount` | 实测 |
| FAQ 列表和搜索 | `POST /api/qa/list` | body：`knowledgeBaseId`、`current`、`pageSize`、`filterType`（必填）、`sortType`（必填）、`keyword?`、`searchMode?`（`semantic` 或 `text`）；每条有 `id`、`question`、`answer`、`isReviewed`、`isAutogenerated`、`duplicateStatus`，按相似度排序时还有 `similarity` | 实测 |
| FAQ 统计 | `GET /api/qa/metrics` | `knowledgeBaseId`；返回 `total`、`reviewed`、`unreviewed` | 实测 |
| FAQ 相似度检查 | `POST /api/qa/check-similarity` | `knowledgeBaseId`、`question`；每条有 `qaId`、`question`、`answer`、`similarity`、`reviewed` | 实测 |
| 文件列表 | `GET /api/knowledge-base/file/list` | `knowledgeBaseId`、`current`、`pageSize`；每条有 `id`（数字）、`name`、`extension`、`status`、`tags` | 实测 |
| 文件详情 | `GET /api/knowledge-base/file/details` | `knowledgeBaseId`、`docId`；返回 `id`、`name`、`docUrl`、`abstract`、`status`、`paragraphCount` 等 | 实测 |
| 段落列表 | `GET /api/knowledge-base/file/paragraphs` | `id`（文件的数字 id，以字符串传）和 `knowledgeBaseId` 都要带；每条有 `id`、`index`、`content`、`wordCount`、`status`。按关键词过滤的 `keyword?` 只在文档里有，没实测 | 实测（`keyword` 为文档） |
| 网页列表 | `GET /api/knowledge-base/web/list` | `knowledgeBaseId`、`current`、`pageSize` | 实测（兴趣岛为空） |

### 2.2 坑（都要在 md 里挡住）

1. **`filterType` 传字符串，结果是错的**【实测】。服务端的参数校验接受 `ALL`、`REVIEWED`、`GENERATED`、`0`、`1`、`2`。但传字符串时，不管传哪个，都只返回未审核的那些，也不报错。传数字才对：0 是全部，1 是已审核，2 是未审核。md 只传数字，并核对「拉到的条数 = `qaCount`」。
2. **段落列表必须带 `knowledgeBaseId`**【实测】，文档里漏写了，缺了返回 400。
3. **列表和详情的字段名不一致**【实测】：列表的 `id`、`fileCount`、`pageCount`，在详情里叫 `knowledgeBaseId`、`docCount`、`webCount`。md 内部统一成一套。
4. **相似度检查返回的 id 叫 `qaId`**，不叫 `id`【实测】。
5. **文件详情用 `docId`，改和删文件用 `id`**【文档】。3b 用得到。

### 2.3 两种「相似度」

09-25 在一个有 140 条 FAQ 的库上探测：

- **语义搜索**：`/qa/list`，`sortType=SIMILARITY`，`searchMode=semantic`【实测】。
  - 拿一条已审核 FAQ 的原问题搜：它自己排第 1，相似度 1.0，后面是 0.86、0.823；一共 5 条，全在本库。
  - 拿一条未审核 FAQ 的原问题搜：它自己不出现。返回的 `page.total` 是 251，比库里的 140 条还多；前 20 条都在本库，分数都在 0.96 左右。`total` 的含义不明（见 §8），md 只用返回的条目，不信 `total`。
  - 结论：未审核的 FAQ 不进语义索引。
- **相似度检查**：`/qa/check-similarity`【实测】。比的是问题和问题，未审核的也查得到：原问题 1.0，第二名 0.86。
- **两者都不是智能体节点的实际打分。** 节点用的是加权重排（见 §2.4），混了关键词。md 只把这两种分数当参考，最后的结论靠 `md trial`。

### 2.4 画布里的知识库引用

来源是本机的画布工作副本【实测】：
- **知识库查询节点**（shape 是 `query-knowledge-base`）：
  - `data.nodePayload` 里有 `knowledgeBaseIds`、`resultCount`（例：5）、`threshold`（例：80）、`rerankType`（例：`weighted`）、`weightedRerankConfig.vectorWeight`（例：0.5）、`modelRerankConfig.modelType`（例：`gte-rerank`），以及 `query`。`query` 引用的是上游节点的输出（`valueType: reference` 加 `dataPath`）。
  - `data.selectKnowledge` 带库名。
  - 节点的输出类型里有 `similarity`、`question`、`answer`、`urlList`、`idList`。
- **大模型挂的知识库工具**：`{ type: 'query_kb', configParams: { knowledgeBaseId } }`。没有召回条数和门槛，用平台默认值。
- 兴趣岛 147bd600 的画布里有 28 个知识库查询节点。
- **执行详情**（`md exec` 已经在用的那份）里有执行时的画布（含上面的配置）和 `nodeResults`（`nodeId`、`inputs`、`output` 等）。本机 66 条执行记录没有一条跑过知识库节点，所以节点运行时的输出结构、分数刻度是 0～1 还是 0～100、和门槛 80 怎么比，开工前要核对（§7）。

## 3. 命令

### 3.1 公共约定

- **知识库的写法**：名字、完整 id，或 4 位以上的 id 前缀。重名或前缀有歧义时列出候选，退出码 4，和 `md bots` 一样。
- **区和企业**：带 `--bot` 时跟着智能体走；不带时用 `--region`、`--org`。只有一个身份、一个企业时（兴趣岛就是）可以省略。
- **输出第一行**：`区 / 企业 / 知识库名 (id 前 8 位)`；带 `--bot` 时是智能体那一行。
- **全部只读**：md 只调 §2.1 里的读接口。测试用的假服务器只要收到写接口的请求，测试就直接失败。
- **隐私**：知识库内容可能有客户资料。完整内容只存在本机的 `~/.miaodong/md/kb/` 下；终端里 FAQ 的问题原样显示，答案和段落只显示前 60 个字。

### 3.2 `md kb list [--bot 智能体 [--version vX]] [--region 区] [--org 企业]`

- **不带 `--bot`**：列出企业里的全部知识库，每个显示名字、id、FAQ 数、文件数、网页数、视频数、向量模型。
- **带 `--bot`**：只列这个智能体引用了的库。默认看草稿，`--version` 看某个版本。
  - 每个知识库查询节点占一行：节点名 [id 前 8 位]、绑定的库、召回条数、门槛、重排方式。
  - 大模型挂的知识库工具占一行：节点名、绑定的库、「平台默认」。
  - 每个被引用的库，附上 FAQ 的未审核数（`/qa/metrics`）。未审核数大于 0 时提示「这些 FAQ 检索不到」。
  - 节点引用了、但企业里已经没有的库，单独标出来：节点绑了一个被删掉的库，永远召回不到东西。

### 3.3 `md kb pull 知识库`

- 拉取范围：全部 FAQ（`filterType=0`，分页）、文件列表、每个文件的详情和全部段落、网页列表。
- 存到 `~/.miaodong/md/kb/<区>/<知识库 id 前 8 位>/<时间>/`，文件是 `faqs.jsonl`、`files.jsonl`、`paragraphs.jsonl`、`webs.jsonl`、`meta.json`。
- **核对**：FAQ 条数要等于 `qaCount`，每个文件的段落数要等于 `paragraphCount`。对不上就报错，多半是接口行为变了，比如 §2.2 第 1 条那种。
- **摘要**：各类条数；未审核多少条；`duplicateStatus` 不是 `normal` 的多少条；状态不是 `ready` 的文件和段落。
- 最后打印本地目录和 jq 用法示例，和 `md pull` 一样。

### 3.4 `md kb find 知识库 "一句话" [--local]`

- 一次查三路：
  1. **文字命中**：FAQ 用 `searchMode=text`，段落用 `keyword` 过滤；
  2. **语义最像**：FAQ 语义搜索的前 10 条，带相似度；
  3. **问题相似**：相似度检查，带相似度，未审核的也在内。
- 每条显示：id、问题（段落则显示开头）、审核状态、重复状态或段落状态、分数。
- `--local`：只在最近一次 pull 下来的本机副本里做文字查找，不发请求。
- 知识库里只有文件、没有 FAQ 时，第 2、3 路跳过，并说明「文件段落没有语义搜索接口，分数要用 `md trial` 看」。

### 3.5 `md kb why 执行id [--node 知识库节点|#序号] [--expect FAQ或段落id|"关键词"]`

目的：一次说清「这次为什么没召回那一条」。步骤：

1. **取执行详情**，和 `md exec` 用同一套逻辑：本地有缓存就用，没有就去拉。这次执行只跑过一个知识库节点时自动选它；跑过多个时列出来，让用 `--node` 指定；一个都没跑过就说明原因并退出（退出码 4）。
2. **看节点**：从执行时的画布取节点配置（绑定的库、召回条数、门槛、重排方式），从节点输入和输出取实际查询的文字和实际召回的条目，从触发输入取用户原话（和 `md exec` 显示的用户消息是同一个来源）。
3. **找「应该召回的那条」**：给了 `--expect`，就按 id 或关键词在绑定的库里找；没给，就用实际查询做语义搜索，把分数最高、但不在实际召回里的前几条列为候选。
4. **逐条判定**：按下表的顺序，报第一个成立的原因，其余成立的作为补充：

| 原因 | 怎么判定 |
|---|---|
| 不在绑定的库里 | 绑定的库里找不到；用文字在企业的其他库里搜到了（报出是哪个库） |
| 未审核 | FAQ 的 `isReviewed` 为 false。未审核的不进语义索引（§2.3） |
| 还在处理 | 段落或文件的 `status` 不是 `ready` |
| 查询被改写 | 实际查询和用户原话不一样；并且用用户原话搜时这条能排进前 N，用实际查询搜时排不进 |
| 分数不够门槛 | 这条对实际查询的语义分数低于门槛。这是按语义分数估计的（§2.3、§8） |
| 被挤出前 N 名 | 分数过了门槛，但排名在召回条数之外 |
| 查不出 | 以上都不成立，给出用 `md trial` 复验的命令 |

5. **输出**：一行结论，每条证据各占一行，最后是下一步：`md trial <节点> --bot … --from-exec <执行id>`，需要换问法时带 `--input`。

这条命令只读，不花钱，也不会自动试跑：试跑要花钱，要走确认码。

## 4. 本地存储与隐私

- 存放位置是 `~/.miaodong/md/kb/<区>/<知识库 id 前 8 位>/<时间>/`，权限和 md 其他本地数据一样，不自动清理，用户可以自己删。
- 终端输出按 §3.1 截断。skill 里写明：AI 不能把知识库全文贴到对话以外的地方。

## 5. 模块

- `src/kb.mjs`：§2.1 接口的封装，统一字段名（§2.2），`filterType` 只传数字。
- `src/kb-refs.mjs`：从画布里取知识库引用（查询节点和大模型工具），纯函数。
- `src/kb-diagnose.mjs`：§3.5 的判定，纯函数。输入是节点配置、实际查询和召回、候选及其状态和分数；输出是原因列表。
- `src/kb-store.mjs`：pull 的落盘和读回。
- `src/commands/kb.mjs`：`list`、`pull`、`find`、`why` 四个子命令。
- skill：`skill/SKILL.md` 加一节「知识库（只读）」；`skill/references/kb.md` 写排查流程、命令和坑。

## 6. 测试

- **假的秒懂知识库服务器**（`test/helpers/kb-server.mjs`）：实现 §2.1 的读接口，并复现 §2.2 的坑：
  - 字符串 `filterType` 只返回未审核的；
  - 段落列表缺 `knowledgeBaseId` 时返回 400；
  - 相似度检查返回 `qaId`；
  - 语义搜索不含未审核的。

  收到任何写接口的请求，测试就判失败。
- **`kb-diagnose`**：每一类原因至少一条用例，外加「多个原因同时成立时，报排在前面的那个」。
- **命令级**：
  - `list`：含 `--bot` 的引用映射、被删的库；
  - `pull`：条数核对，坑被触发时报错；
  - `find`：三路查找、`--local`、只有文件的库；
  - `why`：每一类原因、自动选节点、没跑过知识库节点。
- **产物测试**：`md kb` 在 `dist/md.mjs` 里能在 Node 18 上跑。
- **真机验收**（只读，在兴趣岛）：
  - `md kb list --bot 147bd600`；
  - pull 那个 140 条的库：条数一致，未审核 11 条；
  - `find` 用一条已审核 FAQ 的原问题：它自己排第 1，分数 1.0；
  - `why` 用一条真跑过知识库节点的执行。

## 7. 开工前真跑核对（只读，不花钱）

1. 从线上找一条真跑过知识库节点的执行：先用 `md exec` 按时间窗搜，再逐条看详情。记下节点输入里查询放在哪个字段、输出结构（召回的条目和 `similarity`）、分数刻度是 0～1 还是 0～100，以及它和门槛 80 的关系。
2. `/qa/list` 的 `pageSize` 最大能到多少，决定 pull 大库的速度。
3. 语义搜索的 `page.total` 是什么意思，有没有分数下限：用已审核的原问题搜只回 5 条，用未审核的搜却回 251 条。
4. 段落列表的 `keyword` 过滤是否生效（`md kb find` 的文字命中要用）。

可选，要花一点钱，需要用户同意：在测试专用版上试跑一次知识库节点，对比节点的实际打分和语义搜索的分数，确认「分数不够门槛」能不能直接拿语义分数比。

## 8. 不确定项与假设

- 只在兴趣岛（前端 1.18.4）探测过。其他区，尤其是 I 区 1.17.3，可能缺接口或字段不同；md 遇到时明确报出来，不猜。
- 节点的实际打分是加权重排（向量加关键词），而语义搜索和相似度检查都只看向量。所以「分数不够门槛」和「被挤出前 N 名」是估计：结论里要写明这一点，并给出 `md trial` 的复验命令。
- 【推】知识库没有草稿和发布这一层：改了会立刻对所有引用它的智能体生效。3a 只读，不受影响；3b 设计时再核实。
- 语义搜索的 `page.total` 含义不明，md 不用它。

## 9. 后续（不在本文）

- **3b 导入秒懂**：
  - 支持 FAQ 的新建、修改、审核，以及「手工文件 + 手工段落」；
  - 流程是预演、计划码、写前备份、回读、等向量化完成；能整批撤回，撤回只删这次导入的内容；
