# miaodong-cli 第 3b 步：把处理好的客户资料导入秒懂知识库（带闸门和撤回）

日期：2026-09-25。前置：3a（`md kb list/pull/find/why`，只读，main c9c977d）。

## 1. 目标与边界

用户 09-25 定的规矩（原话）：

> 在查 case 的时候只能读知识库，不能对知识库进行任意的改、写操作！只有在需要处理各种客户资料的时候才能操作知识库。
> 闸门和撤回非常重要。
> 会，有时候要删旧文档重建。

落到 md 上：

- **写知识库只有一条路：`md kb import <导入包>`**。导入包是「处理客户资料」的产物，必须写明来源资料（§3）。md 不提供零散的改、删、审核命令，查 case 时也就没有能改库的命令。这条规矩靠结构保证，不靠提醒。
- 一个导入包里只有两种操作：**加**（FAQ、手工文件 + 段落）和**删**（库里原有的 FAQ、文件，可以不是 md 导入的）。改一条 FAQ = 删旧的 + 加新的。
- **默认目标库挂在线上智能体上**，写进去就对真实用户生效（知识库没有草稿和发布这一层，接口里没有「发布」）。所以闸门按最坏情况设计。
- **每次导入都能撤回**：删掉这次加的，把这次删的从备份原样重建，并且读回核对。

**验收**（全部由自动测试对着假秒懂验证；真实秒懂上的实测见 §10，要用户同意）：

| 指标 | 目标 |
|---|---|
| 写入要用户本人确认 | 不带正确的计划码，一个写请求都不发 |
| 预演 | 0 个写请求；列出目标库、受影响的智能体、增删条数、重复和相似的 FAQ、会备份什么 |
| 闸门没过 | 一条都不写（包格式错、删除对象对不上、要删的东西恢复不了、和现有 FAQ 完全重复） |
| 导入完成后 | 新 FAQ 全部审核通过，每条用自己的问题能搜到；新段落全部 ready；要删的全部不在了 |
| 中途断了（网络、积分、超时） | 记录里知道每一步做到哪；`--resume` 接着做完，不会重复创建 |
| 撤回后 | 这次加的全部不在；这次删的按备份重建，内容逐条相同（id 会变）；读回核对 |

**不做**：FAQ 的图片 / 素材附件（`materialList`、`mhMaterialIds`）；上传原文件（接口没找到，§2.3）；知识标签；数据知识库；网页和视频；新建或删除知识库本身。

## 2. 事实基础

### 2.1 写接口的参数（09-25 从控制台前端代码 1.18.4 里核对）

| 操作 | 接口 | 参数 | 返回 |
|---|---|---|---|
| 批量新建 FAQ | `POST /api/qa/batch-create` | `knowledgeBaseId`, `qaList: [{question, answer, materialList: [], mhMaterialIds: []}]` | 页面只看 `code === 0`，不用返回的 id |
| 批量审核 | `POST /api/qa/batch-review` | `knowledgeBaseId`, `ids` | `code === 0` |
| 批量删除 FAQ | `POST /api/qa/batch-delete` | `knowledgeBaseId`, `ids` | `code === 0` |
| 手工建文件 | `POST /api/knowledge-base/file/manual-create` | `knowledgeBaseId`, `name`（页面限 30 字） | 页面只看 `code === 0`，不用返回的 id |
| 新增手工段落 | `POST /api/knowledge-base/file/manual-create-paragraph` | `knowledgeBaseId`, `docId`, `content` | `code === 0` |
| 删除文件 | `POST /api/knowledge-base/file/delete` | `knowledgeBaseId`, `id` | `code === 0` |
| 更新摘要 | `POST /api/knowledge-base/file/update-abstract` | `knowledgeBaseId`, `docId`, `abstract` | `code === 0` |

- 两个「新建」都不拿返回的 id：md 在写之前记下库里原有的 id（快照），写完列一遍，**不在快照里、问题（或文件名）和包里一致的**就是这次建的。包内问题、文件名不许重复，和库里原有的也不许完全相同（§4），所以这样对得上、不会认错。
- 每批不超过 50 条，串行（接口文档的建议）。

### 2.2 要实测才能确认的（§10）

1. 批量新建的 FAQ 默认是不是**未审核**（接口文档说「可能」）。md 两种情况都能处理：导入流程里本来就有「审核」这一步。
2. 段落的长度上限：页面不限；md 先按 1000 字卡（开放接口的上限）。
3. 新段落从 processing 到 ready 要多久；FAQ 审核后多久能被语义搜索搜到。
4. 写知识库扣不扣积分。

### 2.3 恢复被删的文件：只能恢复成「手工文件 + 原段落」

- 秒懂的文件有原文件（`docUrl`）和段落两部分。检索只用段落，原文件只是给人下载的。
- 把原文件传回秒懂要走对象存储上传，控制台前端里这一步的接口没找到。
- 所以撤回时，被删的文件恢复成**同名的手工文件**，段落原样逐条写回、摘要写回。检索效果和原来一样；差别是原文件不能在秒懂里下载了。原文件在删之前已经下载进本机备份，需要时人工传回。
- 由此定下两条闸门（§4）：
  - 带**知识标签**的文件不能删：恢复不了标签，而模型检索时会按标签过滤。
  - 带**图片 / 素材**的 FAQ 不能删：恢复不了附件。

## 3. 导入包

一个目录，由资料处理（3c）产出；3c 做出来之前，由 AI 按客户资料手工生成。

```
客户A-售后资料-0925/
  manifest.json   目标库、来源资料
  faqs.jsonl      要新增的 FAQ，一行一条
  docs.jsonl      要新增的文件：文件名 + 切好的段落，一行一个文件
  deletes.jsonl   要删的旧 FAQ、旧文件：精确 id + 名字
```

```jsonc
// manifest.json
{ "schema": 1,
  "kb": { "id": "<完整 32 位 id>", "name": "售后 FAQ" },
  "source": { "note": "客户 9 月给的售后手册和价格表",
              "files": [{ "name": "售后手册.docx", "sha256": "<64 位>" }] } }
// faqs.jsonl
{ "key": "f001", "question": "课程怎么退款", "answer": "在订单详情页……" }
// docs.jsonl
{ "key": "d001", "name": "价格表-瑜伽系列", "paragraphs": ["……", "……"] }
// deletes.jsonl
{ "type": "doc", "id": 123, "name": "价格表（旧）" }
{ "type": "faq", "id": 7001, "question": "课程怎么退款" }
```

规则（本地校验，有一处不对，一个请求都不发）：

- `faqs.jsonl`、`docs.jsonl`、`deletes.jsonl` 都可以没有，但三个加起来至少有一条。
- 不认识的字段直接报错，不静默丢掉。
- `key` 在包内唯一，只能用字母、数字、`-`、`_`，最长 64。
- FAQ 的问题、答案去掉首尾空白后不能是空的；包内问题（去掉空白后）不许重复。
- 文件名 1～30 字，包内不许重复；每个文件至少一段；每段去掉首尾空白后不能是空的、不超过 1000 字。
- 要删的：`type` 是 `faq` 或 `doc`；`id` 是正整数；FAQ 要写 `question`，文件要写 `name`；同一个对象不许写两次。
- 来源资料至少一个，每个都要有文件名和 64 位 sha256：没有来源的包不接，这是「只有处理客户资料时才写库」在格式上的体现。
- 导入时把整个包拷进导入记录；包的指纹（四个文件内容的 sha256）进计划码，预演之后包再改动，计划码就对不上。

## 4. 命令与闸门

```
md kb import <包目录> [--confirm <计划码>]
md kb import --resume <导入id> [--confirm <计划码>]
md kb imports
md kb revoke <导入id> [--confirm <计划码>]
```

第一行都是 `区 / 企业 / 知识库名 (id 前 8 位)`。

### 4.1 预演（不带 `--confirm`，只读）

1. 校验导入包（§3）。
2. **找目标库**：在本机身份能看到的企业里按 id 找；找不到退出码 4。秒懂上的库名必须和包里写的一样，不一样退出码 4（防止包导错库）。
3. **核对要删的**：每个 id 都要在库里，FAQ 的问题、文件名要和包里写的一样（去掉首尾空白后比）。不在或对不上，说明包过时了。这几种情况都算**闸门没过**：
   - 要删的 FAQ 带图片 / 素材；
   - 要删的文件带知识标签（§2.3）。
4. **查重复**：
   - 新 FAQ 的问题和库里原有、又不在删除清单里的 FAQ **完全一样**：闸门没过。重复的 FAQ 会互相挤占名次，也会让导入后按问题对 id 时认错。
   - 用相似度检查找出**很像的**（≥ 0.9，未审核的也算）：只列出来，不拦。
   - 新文件名和库里原有、又不删的文件同名：只列出来，不拦。
5. **受影响的智能体**：扫这个企业的全部智能体，看线上版和草稿里哪些节点引用了这个库（大模型节点的知识库工具、知识库查询节点）。
6. **会备份什么**：要删的 FAQ 条数，要删的文件数、段落数，以及要下载的原文件数。
7. 打出计划码。计划码绑定：库 id、包指纹、要删对象当前的状态（FAQ 的问题和答案、文件名、段落数）、增删条数。之后任何一样变了，确认时就对不上，要重新预演。

闸门没过时列出全部原因，退出码 1，不给计划码。

### 4.2 执行（`--confirm <计划码>`）

计划码对不上就停（退出码 5），和推画布一样：计划码要由用户本人确认，AI 不能替用户确认。对上之后按下面的顺序做，每一步做完都写进导入记录（§6），哪一步失败就停在哪一步：

1. **快照**：记下库里现有全部 FAQ 和文件的 id。
2. **备份**：要删的 FAQ 存原始记录；要删的文件存详情、全部段落，并下载原文件（下载不带身份，原文件地址在对象存储上）。段落条数要等于文件详情里的段落数，原文件不能是空的。备份不全就停，这时还一条都没写。
3. **试写一条**：先建 1 条 FAQ（有的话），再建 1 个文件和它的第 1 段（有的话）；读回来逐字核对。对不上就把试写的删掉，然后停下。
4. **建其余的 FAQ**：每批 50 条；全部发完后列一遍库，按「不在快照里、问题一致」对回 id。
5. **建其余的文件和段落**：一个文件一个文件地建：先建文件，列文件对回 id，再逐段写入。
6. **核对内容**：新 FAQ 的问题、答案，以及新文件的每一段，都要和包里的逐字一致。
7. **审核**：新 FAQ 批量审核，读回确认都是已审核。这一步之后它们才对线上生效；在这之前，未审核的 FAQ 检索不到。
8. **等向量化**：新段落全部 ready；每条新 FAQ 用它自己的问题做语义搜索，要能搜到它自己（分数 ≥ 0.99）。默认最多等 8 分钟，没等完就停下，提示稍后 `--resume`。
9. **删旧的**：新内容全部就绪之后，才删要删的 FAQ 和文件，删完读回确认已经不在。先加后删，所以线上不会有「库里什么都没有」的空档。
10. **完成**：打出结果和撤回命令。

### 4.3 续跑（`--resume <导入id>`）

- 预演：说明已经做完哪几步、还剩哪几步，给一个新的计划码（绑定导入 id、当前步骤、剩余条数）。
- 执行前先对账：列一遍库，把「请求发出去了、没收到回复」的那批 FAQ 和文件找回 id。已经建好的不会再建。
- 没写完的文件（段落不全）：先删掉，再从头建。那个文件是这次导入建的，删它不影响别的内容。

## 5. 撤回（`md kb revoke <导入id>`）

- **预演**：
  - 这次建的 FAQ、文件里，哪些还在；哪些在导入后被人改过（问题、答案或段落和导入时不一样）——改过的会列出来，撤回会连改动一起删掉；
  - 这次删的哪些要重建；
  - 给出计划码。
- **执行**，先加后删，和导入同理：
  1. 从备份重建被删的 FAQ：审核状态照原样（原来已审核的，重建后也审核）。
  2. 重建被删的文件：建同名手工文件，逐段写回，写回摘要。
  3. 读回核对重建的内容，并等向量化。
  4. 删掉这次建的 FAQ 和文件，读回确认已经不在。
  5. 导入记录标成「已撤回」，记下重建出来的新 id。
- 导入做到一半的也能撤回：建了多少删多少；还没删旧的，就不用重建。
- 撤回本身也能中断后接着做：再运行一次 `md kb revoke <导入id>`，预演会说明还剩什么。

## 6. 导入记录与本地存储

`~/.miaodong/md/kb-imports/<区>/<知识库 id 前 8 位>/<导入id>/`，目录 0700，内容文件 0600：

```
package/        导入包的拷贝
snapshot.json   执行前库里的 FAQ id、文件 id
backup/         要删的 FAQ（faqs.jsonl）、文件（docs/<id>/detail.json、paragraphs.jsonl、原文件）
state.json      做到哪一步、key → 秒懂 id、各步时间
log.jsonl       每个写请求：操作、条数、id、结果（不记内容）
```

- 导入 id 是 `时间-包指纹前 4 位`。
- `md kb imports` 列出本机的全部导入记录：时间、区、库、增删条数、状态（进行中、已完成、已撤回、停在第几步）。
- 备份里有客户资料，只存本机，不自动清理。

## 7. 模块

- `src/kb-write.mjs`：§2.1 的写接口封装，以及备份要用的原始读取（FAQ 原始行、文件详情原始字段、下载原文件——不带身份）。
- `src/kb-package.mjs`：读导入包、严格校验、算指纹。纯函数为主。
- `src/kb-import-store.mjs`：导入记录的目录、状态、日志、备份读写，列出全部记录。
- `src/kb-import-plan.mjs`：预演：找目标库、核对要删的、查重复、受影响的智能体、计划码。
- `src/kb-import-run.mjs`：执行和续跑（§4.2、§4.3），以及撤回（§5）共用的步骤：对账、核对、等向量化。
- `src/commands/kb-import.mjs`、`src/commands/kb-revoke.mjs`：命令入口；`src/commands/kb.mjs` 登记 `import`、`imports`、`revoke`。
- skill：`skill/references/kb-import.md` 写流程和规矩；`skill/SKILL.md` 的知识库一节补上「只在处理客户资料时导入，查 case 时绝不写」。

## 8. 测试

假秒懂（`test/helpers/kb-write-server.mjs`）在 3a 的读接口之上加 §2.1 的写接口，行为照真实的来：

- 新建不返回 id；新 FAQ 默认未审核；
- 新段落先是 processing，被读几次之后变 ready；
- 原文件从假服务器下载；
- 可以指定第几次调用某个接口时失败（502），模拟中途断掉；
- 记下每个写请求，供断言。

用例：

- 预演：0 个写请求；各类闸门没过时，一条都不写。
- 计划码：不对就停；包或删除对象在预演之后变了也停。
- 顺利导入：步骤齐全，结果符合 §1 的验收。
- 试写一条就对不上：删掉试写的那条，然后停下。
- 第 k 批失败：续跑之后完成，不重复创建。
- 等向量化超时：续跑之后完成。
- 撤回：顺利撤回；导入到一半时撤回；导入后被人改过的条目要列出来；撤回做到一半中断，再跑一次接着做。
- 下载原文件时不带 Authorization。
- 产物测试：`md kb import` 能在 Node 18 上跑。

## 9. 实施顺序

1. `kb-package`（校验、指纹）。
2. `kb-write` 和假秒懂的写接口。
3. `kb-import-store`（记录、状态、备份）。
4. `kb-import-plan` 和预演命令。
5. 执行：快照、备份、试写、建 FAQ、建文件、核对、审核、等向量化、删旧的。
6. 续跑。
7. 撤回。
8. `md kb imports`，文档，产物测试。

## 10. 正式用之前在真实秒懂上的实测（要用户同意，并指定一个测试库）

1. 在测试库上导入一个小包（3 条 FAQ、1 个文件 2 段、删 1 条 FAQ、删 1 个文件）。核对 §2.2 的 4 个问题，以及试写、对账、审核、等向量化、删旧的各步。
2. 撤回这次导入：核对重建的内容和备份一致，这次建的都删掉了。
3. 中途打断一次（比如在建 FAQ 时断网），再续跑。
4. 用实测结果修正 §2.2 里的假设（段落长度上限、等向量化的默认时长），再发版给同事用。
